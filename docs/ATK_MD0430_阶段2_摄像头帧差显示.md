适用：Vivado / SDK 2018.3，STUDYBOARD Zynq-7020，OV5640，ATK-MD0430 V2.0（NT35510、8080 16 位接口）。工程根目录：`E:/zynq/github/ZYNQ_ov5640_hdmi_frame_difference-master`。

阶段 1 的彩条已由你在实物上验证。阶段 2 的目标是：在 800×480 LCD 中央显示 640×480 摄像头画面，左右各留 80 像素黑边，并叠加运动检测白框。软件和仿真能验证设计逻辑；摄像头实时画面、实际帧率、杜邦线信号质量仍需要本次上板确认。

## 1. 先认识这一版实际的数据流

```text
PS Cortex-A9 裸机程序
  ├─ EMIO GPIO / SCCB：读 OV5640 ID，写分辨率、像素格式等寄存器
  └─ AXI GP0 / AXI4-Lite：配置 VDMA 的地址、行宽、行数、运行方式

OV5640：RGB565，每个像素分两个 8 位 DVP 时钟传输
  │ D[7:0]、PCLK、HREF、VSYNC
  ▼
ov5640_capture_data：拼合 RGB565，扩展成 24 位 RGB888 容器
  │ 24 位像素、有效标志、行/场同步；仍在摄像头 PCLK 域
  ▼
Video In to AXI4-Stream：跨时钟 FIFO，转换成 100 MHz AXI 视频流
  │ TDATA[23:0]、TVALID、TREADY、TUSER、TLAST
  ▼
frame_difference_axis_bram：8×8 网格中心采样 → 与上一帧亮度比较
  │ 2 个 RAMB36 保存 4800 个历史采样；邻域筛选 → 单个包围框
  │ 原始像素直通，边框像素改为白色
  ▼
VDMA0 的 S2MM → AXI 内存映射突发 → HP0 → PS DDR
  │ 三个 RGB888 帧缓冲区，每帧 921600 字节
  ▼
PS DDR → HP1 → VDMA1 的 MM2S → AXI4-Stream
  ▼
axis_nt35510_display：LCD 初始化完成后交接总线
  ▼
axis_lcd_frame_writer：清屏、设置窗口、RGB888 → RGB565、AXI 反压
  ▼
lcd8080_write_cycle：生成 CS / RS / WR / D[15:0]
  ▼
NT35510 内部 GRAM → LCD 控制器自行扫描面板
```

这一版帧差历史在 PL 的 BRAM 中，**不读取 DDR 的上一整帧做差分**。Block Design 中保留了 VDMA0 MM2S 到 `S1_AXIS` 的旧连接，但应用只启动 VDMA0 的 `ONLY_WRITE`，新帧差模块也不使用 S1 的数据。这样阅读工程时就不会把未运行的兼容连接误认为算法必经路径。

摄像头原始有效色深是 RGB565。扩展成 RGB888 是为了适配现有 AXI 视频/VDMA 数据宽度，低位补零不会产生新的颜色细节；最后截回 RGB565 正好对应 LCD 格式。

## 2. 每种接口负责什么

| 接口 | 本工程用途 | 必须理解的规则 |
| --- | --- | --- |
| SCCB | PS 配置 OV5640 寄存器 | SCL/SDA 传控制数据，不传视频；读出 `0x5640` 只证明摄像头控制通信成功 |
| DVP | 摄像头送出像素 | 摄像头主动产生 PCLK；HREF 内每两个字节组成一个 RGB565 像素；不能用 AXI 的 TREADY 直接暂停摄像头 |
| AXI4-Stream Video | PL 模块之间传视频 | 只有 `TVALID && TREADY` 时才交付一个像素；TUSER 标记帧首像素，TLAST 标记每行最后一个像素 |
| AXI4-Lite | PS 配置 VDMA | 访问寄存器，地址为 `0x43000000` 和 `0x43010000`；不是像素存储地址 |
| AXI 内存映射 / HP | VDMA 读写 DDR | 由地址和突发传输搬运帧数据；HP0 写采集结果，HP1 读显示数据 |
| Intel 8080-16 | FPGA 写 LCD | RS=0 写命令/寄存器地址，RS=1 写参数或像素；WR 上升沿结束一次写入，RD 保持高 |

AXI 反压示例：LCD 正在发送窗口命令时，`TREADY=0`。VDMA1 必须保持当前像素、TUSER、TLAST 不变。窗口命令发送完后才拉高 TREADY 接走首像素。DDR 把这个慢速显示过程与前面的摄像头采集隔开。

## 3. 新增模块与函数的阅读顺序

| 文件 | 重点 |
| --- | --- |
| `SDK/ov5640_lcd_frame_difference/main.c` | 从 PS 初始化顺序入手；这里没有 HDMI/VTC/dynclk 初始化 |
| `rtl/frame_difference_axis_bram.v` | 看采样地址、同步 BRAM 读写、亮度差、邻域确认和白框叠加 |
| `rtl/axis_nt35510_display.v` | 看初始化引擎和视频引擎怎样共享 LCD 引脚 |
| `rtl/axis_lcd_frame_writer.v` | 看清屏状态机、窗口命令、像素握手、帧结束计数 |
| `bringup/atk_md0430_colorbar/lcd8080_write_cycle.v` | 看一次总线写周期；阶段 2 使用 `CYCLE_DIV=2` |
| `bringup/atk_md0430_colorbar/atk_md0430_colorbar_top.v` | 复用阶段 1 已验证的 NT35510 初始化表与彩条自检 |
| `constraints/studyboard_lcd_top.xdc` | 摄像头和 J7 LCD 管脚；接线沿用成功的彩条方案 |
| `scripts/create_studyboard_lcd_project.tcl` | 可逐行复现的 PS、IP 参数、AXI/时钟/复位连接与地址分配 |

`main.c` 的函数顺序如下：

1. `reset_video_fabric()`：通过 SLCR 的 FPGA_RESET0 复位视频逻辑，并等待时钟和复位同步器稳定。
2. `initialize_camera()`：初始化 EMIO SCCB，重试读取芯片 ID，再调用 `ov5640_init(640, 480, 2570, 980)`。
3. `memset()` + `Xil_DCacheFlushRange()`：清零三个帧缓冲，确保 DMA 启动时读到确定的黑色数据。DMA 运行以后 CPU 不再访问这些像素。
4. `run_vdma_frame_buffer(... ONLY_WRITE)`：VDMA0 将处理后像素写入 DDR。
5. `run_vdma_frame_buffer(... ONLY_READ)`：VDMA1 从同一组缓冲读出供 LCD 使用。
6. 打印两个有效通道的错误状态，CPU 留在等待循环；PL 和 DMA 自行持续工作。

公共 `vdma_api.c` 中，`WriteSetup()` / `ReadSetup()` 设置 VSIZE、HSIZE、STRIDE 和帧地址；`StartTransfer()` 启动对应通道。640×480 RGB888 的参数必须是：`VSIZE=480`、`HSIZE=1920`、`STRIDE=1920`。HSIZE 和 STRIDE 的单位是**字节**，不能填 640。

帧缓冲起点由 BSP 的 DDR 基地址加 `0x01000000` 计算，实际数值以编译后宏和串口打印为准。后两帧分别再加 `0x000E1000` 和 `0x001C2000`。三个缓冲共 2764800 字节。

## 4. 帧差算法，不等于目标识别

每 8×8 像素选一个中心点，因此 640×480 得到 80×60=4800 个采样点。亮度近似为 `Y=(R>>2)+(G>>1)+(B>>2)`。将当前采样亮度与 BRAM 中上一帧同位置亮度相减，绝对值大于 40 时标为变化。

单个变化点容易来自噪声。当前点还需要左邻或上邻也发生变化才进入包围框统计。网格最外圈不参与有效运动统计；确认点数小于 2 或大于 1000 时不显示框，减少孤立噪声和全局亮度变化的影响。有效点扩展一个采样块后合并成一个矩形，下一帧把边界附近两像素改成白色。

所以它会框住“变化区域”，不能区分人脸、手、屏幕闪烁或光照变化；多个运动物体也可能合并为一个大框。摄像头固定、场景稳定后挥手，是比晃动摄像头更合适的实验。

历史亮度同步读写只有一个时钟延迟。每两个采样点至少相隔 8 个有效像素，足够在下一个采样前完成差值处理。BRAM 本身不做异步复位；首帧只建立历史，`history_valid` 在完整首帧结束后使能检测。

工程重建时曾发现旧源码的异步数组访问产生巨大 LUT 选择网络，且已有缓存网表与源文件不能仅凭时间戳证明一致。新增模块用同步 RAM 访问消除这一问题；构建脚本会重置各 OOC 综合结果，确保使用当前源码。

## 5. LCD 状态机与速度

初始化引擎完成硬件复位、NT35510 寄存器配置、退出休眠、横屏与 RGB565 设置，然后写入彩条并打开背光。`init_bl` 成为总线交接标志；视频写入器随后清黑 800×480，再等待 AXI 帧首。

每帧先写 `0x2A00..0x2A03` 设置 X=80..719，写 `0x2B00..0x2B03` 设置 Y=0..479，写 `0x2C00` 开始 GRAM 写入，再传入 307200 个 RGB565 像素。窗口地址和像素由同一个底层写周期模块发送。

100 MHz 系统时钟下，底层 `CYCLE_DIV=2` 使数据建立时间为 20 ns，WR 低电平保持 40 ns，复用彩条验证过的外部时序。加上上下层握手，连续像素请求约每 11 个系统时钟一次，理想传输上限约为 `100 MHz / 11 / (640×480) ≈ 29.6 帧/秒`；命令、AXI 等待和 DDR 竞争会降低实际结果。这个数值是接口吞吐估计，不是已测摄像头帧率，也不是面板扫描刷新率。

彩条到清屏的交接很快，肉眼可能只看到闪一下或直接看到黑屏。摄像头采集模块还会等待约 10 个 VSYNC 周期稳定，因此启动后的短暂黑屏不一定是故障。

## 8. 验证证据和故障定位

| 验证 | 方法与意义 |
| --- | --- |
| LCD 接线/初始化 | 你已看到完整彩条，证明当前实物基本通信正常 |
| 帧差行为 | `simulate_frame_difference_axis_bram.tcl` 使用小图像序列检验历史、差分、边框及像素传递 |
| BRAM 推断 | `synthesize_frame_difference_axis_bram.tcl` 检查 RAMB 原语数量；独立综合为 2 个 RAMB36 |
| LCD 数据转换 | `simulate_axis_lcd_frame_writer.tcl` 在 WR 上升沿记录命令/像素，检验清屏、居中窗口、RGB565 颜色和 AXI 握手 |
| 完整时序/资源 | `output/lcd_full/timing_summary.rpt`、`utilization.rpt` |
| 实物完整视频 | 下载本阶段 bit + ELF 后观察；需由本次上板结果确认 |

| 现象 | 首先检查 |
| --- | --- |
| 没有串口横幅 | ELF 是否运行、是否停在 main、串口是否选对 |
| 摄像头 ID 不是 0x5640 | 摄像头供电、SCCB、XCLK；暂时不用修改 LCD |
| 只有短暂彩条然后一直黑屏 | 先看摄像头 ID 和两个 VDMA ERR；ERR=0 也不证明收到了完整视频 |
| 画面只有第一次更新 | 检查两个 VDMA 是否仍运行，再观察 S2MM 写帧索引和 LCD 帧计数 |
| 颜色错位 | 核对 RGB 通道次序、RGB565 位切片和 LCD D0..D15 接线 |
| 图像撕裂或偶尔跳回旧帧 | 当前独立循环缓冲缺少完成帧交接机制，见下一节 |

`axis_lcd_frame_writer` 内有 `displayed_frame_count`、`axis_protocol_error`、`init_clear_done` 便于后续增加 ILA。当前顶层没有导出这些诊断量，综合可能优化掉它们；需要观测时应显式接到 ILA 或可读状态寄存器后重新生成 bit，不能直接假定现有 bit 中有调试核。

如果画面几何位置、实时刷新和白框都正常，唯独红绿蓝颜色不对，先不要改 VDMA 或摄像头时序。LCD 端唯一的 RGB888→RGB565 切片位于 `rtl/axis_lcd_frame_writer.v`：

```verilog
{s_axis_tdata[23:19], s_axis_tdata[15:10], s_axis_tdata[7:3]}
```

当前约定为 `[23:16]=R`、`[15:8]=G`、`[7:0]=B`。用镜头依次对准纯红、纯绿、纯蓝物体，记录显示结果；若只是两种颜色互换，就只交换对应位段后重建 bit。这个测试能把“AXI 通道次序错误”与“D0..D15 物理接反”区分开：物理数据位接反通常还会出现亮度和渐变异常，不只是整组颜色互换。

## 9. 接通之后如何继续开发

先拿到一段连续移动的实物画面，再按下面顺序推进：

1. **完成帧交接**：目前两个 VDMA 使用相同三个地址、独立循环，没有 genlock 或软件帧所有权管理，因此可能读到正在写的帧或重复读到旧帧。后续通过写完成事件、读帧边界与帧索引管理，确保显示只取已完成帧；仅配置“三缓冲”不会自动解决撕裂。
2. **800×480 满屏**：同时修改摄像头活动尺寸、帧差参数、LCD 输入窗口和 X_OFFSET、C 程序尺寸与帧缓冲大小，再确认 VDMA 行字节数为 2400。必须检查 OV5640 裁剪/缩放及采样数组范围，不能只改一个宏。当前帧差 x/y、网格坐标和采样地址位宽适用于这一尺度；继续增大尺寸要重新计算位宽。
3. **调整摄像头帧率**：`ov5640_init()` 的后两个参数是行/帧总时序相关参数，分辨率参数是前两个。实际帧率还取决于传感器 PLL、时钟分频、曝光和消隐。先保持寄存器表，测量 VSYNC 周期，再一次只改一个因素；XDC 的 `create_clock` 只约束时序分析，不会替摄像头改变输出帧率。
4. **提升 LCD 吞吐**：当前约 29.6 fps 的 640×480 写入上限来自保守写周期；800×480 同样时序的理想上限约 23.7 fps。应先验证布线和器件时序，再减少握手空闲或调低周期参数，不能把修改 FCLK 当作无条件提速方法。
5. **Linux / 人脸模型**：保留 PL 采集、帧差、LCD 通路；Linux 需要设备树、时钟/复位、DMA 缓冲分配与缓存一致性管理，不能照搬裸机固定物理地址当作普通内存。先做到用户态能取得完整帧，再在 Cortex-A9 上用小输入模型测推理耗时。人脸检测模型输出矩形，显示端再叠框；这属于识别算法，与当前帧差白框不是同一种功能。模型是否够快应通过板上实测确定。

本阶段优先理解并验证完整像素链路。先记录串口启动日志、移动物体的视频表现、颜色和左右黑边，再决定优化帧交接还是分辨率。
