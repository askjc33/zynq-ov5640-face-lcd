# 01｜系统架构与核心概念

## 1. 一句话理解项目

它不是“摄像头直接把图像送进神经网络”：OV5640 先以 DVP 输出视频，PL 把像素流送进 VDMA/DDR；Linux 驱动把完成的 DDR 帧作为 V4L2 采集缓冲交给用户程序；用户程序挑最新帧做 NCNN 推理，再把带框 BGR24 帧交给独立的 LCD 显示 DMA。**视频采集、推理、显示是三种不同的速率和所有权。**

```text
OV5640 /dev/i2c-0 0x3c  ← Linux 通过 SCCB/I²C 写寄存器
       │ DVP RGB565 像素流
       ▼
PL 接收/颜色转换（板上 bitstream 若含帧差模块，还可能先画运动框）
                   → VDMA0 S2MM → DDR 中的 vb2 捕获缓冲
                                  │ /dev/video0, V4L2 MMAP
                                  ▼
                 用户态采集线程：DQBUF → 复制最新完整帧 → QBUF
                                  │ 双槽邮箱（只保留最新）
                                  ▼
                 用户态推理线程：letterbox → NCNN → NMS → 原图坐标
                                  │ 检测框和/或带框原图
                                  ▼
               用户态 LCD 传输 → lcd_frame / lcd_commit
                                  │ 独立 coherent 显示缓冲
                                  ▼
                         VDMA1 MM2S → PL LCD 控制器 → LCD
```

设备树 `linux/studyboard_frame_capture/studyboard-frame-capture.dtsi` 用 `dma-names = "capture", "display"` 把 VDMA0 的 S2MM 和 VDMA1 的 MM2S 交给同一个 platform 驱动。S2MM 是“流到内存”，MM2S 是“内存到流”。`probe()` 获取两个 DMA 通道、分配显示/诊断缓冲并注册 `/dev/videoX`，**加载模块本身不启动摄像头或显示 DMA**。仓库中的 LCD Block Design 包含 `frame_difference_axis_bram`，它的运动框与 NCNN 人脸框是两套算法；当前板上是否装载该确切 bitstream 仍需用启动文件/XSA 版本核对。

## 2. 像素格式和内存计算

传感器配置表把 OV5640 设为 640×480 RGB565 DVP；PL 后续通路把它转换为逻辑 RGB888。内核驱动对 CPU 可见的连续内存约定是 **B、G、R** 三字节，因此 V4L2 fourcc 为 `BGR3`（`V4L2_PIX_FMT_BGR24`），不能因为硬件逻辑名为 RGB888 就把用户态数据按 RGB24 解读。

| 量 | 算法 | 当前值 |
| --- | --- | ---: |
| 一行跨度 | 640 × 3 字节 | 1920 字节 |
| 一帧 payload | 1920 × 480 | 921600 字节 |
| 旧诊断/显示三帧 coherent 区 | 921600 × 3 | 2764800 字节 |
| V4L2 缓冲 | 用户程序请求 4 个 MMAP 帧；由 vb2 另行分配 | 不与上述显示缓冲混用 |

`lcd_frame` 接收的是**恰好 921600 字节的裸 BGR24 像素**，不能写 PPM 文件头、JPEG 或 PNG。`face-lcd-last.ppm` 则是给 PC 查看的一份独立文件：它包含 PPM 头和 RGB 像素，不能直接提交给 `lcd_frame`。

## 3. V4L2/MMAP：谁在什么时候拥有一帧

内核 V4L2/videobuf2 负责缓冲分配、排队、完成通知和用户态映射；本项目的应用仍在**用户空间**。主程序的顺序是：

```text
open /dev/video0 → QUERYCAP → S_FMT(BGR24 640×480)
→ REQBUFS(4, MMAP) → QUERYBUF/mmap → 全部 QBUF → STREAMON
→ poll → DQBUF(取得一张已完成帧) → 校验 sequence/bytesused
→ 复制到用户态双槽邮箱 → 立即 QBUF(归还给驱动) → 重复
→ STREAMOFF → munmap/close
```

`QBUF` 后缓冲属于驱动/DMA，应用不能假设它不变；`DQBUF` 后应用临时拥有完成帧。推理可能需要 383–1025 ms，而摄像头约 35 ms 来一帧，因此应用**复制完成帧后立即 QBUF**，不让一个慢推理长期占住 vb2 缓冲。内核帧完成回调设置 `sequence`、时间戳、`bytesused=921600`，再调用 `vb2_buffer_done()`。驱动在打开 `/dev/video0` 时取得独占采集所有权；旧 sysfs `running=1` 不能同时占用 VDMA0。

两个用户态邮箱槽位不是 V4L2 帧，也不是 LCD 帧。采集线程只写未被推理线程占用的槽位，发布 `latest_generation` 并唤醒工作线程；推理线程醒来只取**最新**完整帧。中途到来的旧帧可被新帧覆盖，所以 `skipped_stale = captured - processed` 是低延迟策略，不是内核丢帧。真正的连续性要看 `sequence_gaps` 与 `bad_payloads`。内核/用户态 MMAP 的通用语义可对照 [Linux V4L2 Memory Mapping 文档](https://docs.kernel.org/5.17/userspace-api/media/v4l/mmap.html)。

## 4. 模型数据怎样从 640×480 变为方形

`FaceDetector::detect()` 用 NCNN 同时完成 BGR→RGB 和双线性缩放，再以像素值 114 补边、乘 `1/255`，得到 RGB float32 CHW。**保持比例的 letterbox 不是把 640×480 强行拉成正方形**：

| 输入尺寸 | 原图缩放后 | 上/下补边 | 输出候选数 |
| ---: | ---: | ---: | ---: |
| 320 | 320×240 | 各 40 | 2100 |
| 256 | 256×192 | 各 32 | 1344 |
| 224 | 224×168 | 各 28 | 1029 |
| 192 | 192×144 | 各 24 | 756 |

候选数来自三个检测步长：`(S/8)² + (S/16)² + (S/32)²`。NCNN blob 名为 `in0`、`out0`，单类模型的输出按本导出版本读作 5 行：中心 x、中心 y、框宽、框高、人脸分数。C++ 代码先过滤分数，再做同类 NMS；逆映射时减去补边、除以缩放比例、裁剪到 640×480。比如 192 输入的 y 坐标回原图时必须减去 24，**不能继续用 320 输入的 40**。代码会检查输出候选数，不匹配尺寸时直接失败，避免静默读错模型。

独立 `studyboard-v4l2-preprocess` 的 224×224 性能实验只验证预处理能力；当前人脸应用有自己的 letterbox 流程，不能把两者的耗时或像素布局混为一谈。

## 5. LCD matched 与 preview 两种语义

| 模式 | 屏幕上是什么 | 优点与限制 |
| --- | --- | --- |
| `matched` | **本次推理的那一张原图**及其本次框 | 图框严格一致；画面更新频率约等于推理频率。 |
| `preview` | 较新的采集图＋最近一次已完成的框 | 背景较流畅；人移动时框可能滞后，超过 60 个采集序号约 2 秒仍未更新则隐藏。 |

应用分块写 `lcd_frame` 的后台缓冲；只有整帧写完才向 `lcd_commit` 写 `1`。驱动第一次发布时启动持续运行的 VDMA1 MM2S；后续把完整后台帧复制到前台，不停 DMA。这样避免把“只写了一半的用户图像”直接作为新帧发布，但 **前台 memcpy 可能与 MM2S 读取重叠，尚不保证严格无撕裂**。这不是标准 V4L2 output，也不是 `/dev/fb0`。V4L2 负责采集，`lcd_frame/lcd_commit/lcd_status` 是本项目的显示扩展。

## 6. 四种常被混淆的速度

1. **采集 fps**：`capture_summary` 中摄像头进入用户态的完成帧，约 28.5。
2. **推理 fps**：`average_ms: inference` 推导出的模型频率；320 约 0.98，192 约 2.61。这不是整个端到端延迟。
3. **LCD 发布率**：`lcd_summary.frames / capture_summary.seconds`；preview 中约每秒十余次，只说明送了多少张图，不能证明 LCD 物理刷新率或每张都有新检测。
4. **端到端感知延迟**：从现实中脸移动到屏上框更新的时间；本项目尚未用统一时钟/测试物专门测量，不能由上述任一数字直接替代。

从统计理解：`total_faces` 是**各次处理帧的检出框数之和**，不是“多少个不同的人”；不同时间段的值也不能直接计算模型召回率。一次框是否正确仍要看标注/目视与相同场景对照。
