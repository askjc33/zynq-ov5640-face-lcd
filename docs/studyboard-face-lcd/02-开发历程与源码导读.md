# 02｜开发历程、源码导读与复现知识

本章按照“先证明一个环节，再叠加下一环节”的实际开发顺序讲解。**代码中的注释是实现意图；是否成功以板端日志和实物观察为准。**源文件均位于仓库的 `linux/` 目录，完整逐次证据在根目录开发记录中。

## 1. 分阶段开发，而不是一次写完整系统

| 阶段 | 当时要回答的问题 | 最小验证/形成的接口 |
| --- | --- | --- |
| 传感器 | Linux 能否通过 SCCB/I²C 找到并配置 OV5640？ | `ov5640-id` 读到 `0x5640`；`ov5640-init` 写 248 项，关键寄存器和 640×480/2570×980 读回。 |
| PL/VDMA | 像素流是否真的进 DDR？ | 先用诊断 sysfs、快照/摘要和 DMA 中断分段排查。I²C PASS 不替代这一步。 |
| V4L2 | 能否让普通 Linux 应用按标准缓冲队列抓帧？ | 注册 `/dev/video0`；MMAP 抓 1000 帧完整，后来轻量应用稳定约 28.5 fps。 |
| 预处理 | BGR 字节序、缩放和 CHW 能否正确且足够快？ | 独立 224×224 工具 300 帧，平均处理约 22.705 ms。 |
| 模型 | 训练结果能否在 ARM 真实图像上给出人脸框？ | YOLOv8n 单类训练 → NCNN 模型 → ARM 应用输出 score/box，保存 PPM 目视通过。 |
| LCD matched | “本次图＋本次框”能否送上物理屏？ | 自定义 LCD sysfs＋VDMA1 持续 MM2S，用户看到红框。 |
| LCD preview/持久化 | 背景画面能否持续更新，重启后能否恢复？ | 双线程预览、SD 独立运行包、9000 帧长测、重启/重新上电后手动启动。 |
| 速度优化 | 约 1 fps 的瓶颈在哪、减小模型输入是否有效？ | 双核 SIMPLEOMP；同权重 192/224/256/320 上板对照，192 约 2.61 fps。 |

这种分层验证非常重要：如果只看到 `faces=0`，首先应确认 V4L2 图像像素正确，再怀疑模型；如果 V4L2 连 frame 0 都没有，应回看 PL/VDMA/传感器，而不是改 NMS 阈值。

## 2. 硬件描述和传感器代码

`linux/studyboard_frame_capture/studyboard-frame-capture.dtsi` 声明 platform 设备及两个 DMA 通道。`width=640`、`height=480`、`bytes-per-pixel=3`、`frame-count=3` 是当前驱动的固定几何约定。改变传感器分辨率不能只改一处：PL 时序、设备树、驱动 stride/sizeimage、应用常量、模型坐标映射和 LCD 尺寸都必须一致。

`linux/ov5640_init/ov5640-init.c` 通过 `/dev/i2c-0` 的 `I2C_RDWR` 发两个地址字节＋一个数据字节，向器件地址 `0x3c` 写 16 位寄存器地址。`ov5640-init-table.h` 保存经验证的寄存器序列。程序先读芯片 ID，再逐项写；写失败时对**同一个寄存器**最多尝试 10 次、间隔 5 ms，而不是整张表无限重放。最后读回时钟、PLL、RGB565/ISP/测试图和有效尺寸等关键值。这个设计解决了曾经 `Write 7/248 reg=0x3108` NAK 的局部失败，但读回通过仍不证明 PL 收到了 DVP 帧。

## 3. 内核驱动怎么把 DMA 变成 `/dev/video0`

主文件 `linux/studyboard_frame_capture/studyboard-frame-capture.c` 可按下列顺序阅读：

1. `struct studyboard_capture`：一个设备实例的总状态，含 DMA 通道、CPU/DMA 地址、vb2 队列、锁、显示前后台和统计。`buffer_cpu` 是内核 CPU 虚拟地址；`buffer_dma` 是 DMA 总线地址，不能互换。
2. `studyboard_capture_probe()`：读取设备树、`dma_request_chan()`、`dma_alloc_coherent()`、创建 sysfs 文件、初始化 vb2 并注册 video 节点。失败路径倒序清理；`remove()` 先停使用者/DMA 再释放内存，防止硬件访问已释放内存。
3. `studyboard_v4l2_queue_setup()`/`buffer_queue()`：要求至少 3 个缓冲、每帧 921600 字节；从 `vb2_dma_contig_plane_dma_addr()` 取得 DMA 地址，提交一帧 interleaved 描述符。
4. `studyboard_v4l2_frame_done()`：DMA 完成后写 sequence/时间戳/payload，再调用 `vb2_buffer_done()`；`start_streaming()`/`stop_streaming()` 负责启动和终止 DMA。
5. `studyboard_v4l2_open()`/`release()`：在打开时即取得独占 owner，防止已排队的 V4L2 描述符与旧 sysfs `running=1` 抢同一个 S2MM 通道；关闭时清理会话。
6. `lcd_frame_write()`/`lcd_commit_store()`：连续偏移分块写后台，整帧写完才 commit；`studyboard_start_lcd_display()` 把 VDMA1 设置为持续 MM2S，`studyboard_publish_lcd()` 完成后续前台帧复制。

驱动另保留 `running`、`display_running`、`snapshot_raw` 等诊断接口，它们用于早期 bring-up；**正常人脸应用只用 V4L2 采集＋专用 LCD 输出**。`callback_count` 是软件描述符回调计数，不等于摄像头持续帧率；进入硬件循环后应综合 V4L2 sequence 和 `/proc/interrupts` 判断。

为什么不继续让应用从自定义 sysfs 抓帧？V4L2/vb2 已提供标准的格式协商、MMAP 缓冲、QBUF/DQBUF、poll、时间戳和释放语义；sysfs 快照适合诊断，不适合作为长期采集协议。但 V4L2 不替代传感器配置、PL 像素处理、VDMA 或本项目的 LCD 显示通路。

## 4. 用户程序里的两个线程与三个源文件

`linux/studyboard_ncnn_face/studyboard-ncnn-face.cpp` 是入口：解析参数、打开 `/dev/video0`、申请 4 个 MMAP 缓冲、启动采集与推理线程、打印汇总并清理。核心不变量是：**每次 DQBUF 只做短复制并尽快 QBUF；推理不持有 vb2 缓冲**。`LatestFrameMailbox` 有两张完整帧副本、mutex/condition、最新代数和 `processing_slot`。当推理落后时旧帧被替换，保持延迟不随着队列积压增长。

`linux/studyboard_ncnn_face/face_detector.cpp` 加载 `model.ncnn.param/bin`，执行 BGR→RGB、缩放、letterbox、归一化、NCNN `in0/out0`、置信度过滤和 NMS。输入尺寸可选 192、224、256、320，形状必须与对应导出模型配套。`draw_face_detections_bgr()` 只在用户态副本上画红框；`write_bgr24_ppm()` 用于把最后一张带框图保存为 PC 可查看的 PPM。

`linux/studyboard_ncnn_face/lcd_output.cpp` 是显示传输适配层：验证 `lcd_frame` 大小，分块写恰好一帧，然后向 `lcd_commit` 写 `1`；退出时写 `0` 停显示。它不会解析神经网络，也不会修改 V4L2 MMAP 捕获缓冲。`preview` 模式由采集线程较频繁地发布新画面，推理线程更新最近一次框；`matched` 模式只发布推理对应的原图与框。

## 5. 训练、导出和版本锁：哪些是事实，哪些不是

本机实际训练记录 `E:/Yolo/face_zynq/runs/face_yolov8n_320/args.yaml`：数据配置在 `E:/Yolo/ultralytics-main/newface/data.yaml`，单类 `face`；目录中现有图片/标签数量为 train 771、valid 19、test 108。模型起点为 `yolov8n.pt`，目标 `epochs=100`、`patience=30`、`batch=8`、`imgsz=320`、`device=0`、`seed=42`；训练在 89 个 epoch 后早停，最佳权重来自第 59 个 epoch。**不要把“设置 100 epoch”误写成“训练跑满 100 epoch”。**

当时 19 张验证图上 P≈0.996、R=1.000、mAP50=0.995、mAP50-95=0.944。后续同一 `best.pt` 在复制的 108 张 test 图上按不同方形输入测试，mAP50 均约 0.995，mAP50-95 为 320:0.9628、256:0.9636、224:0.9726、192:0.9577。该 test 每图一张标注人脸；这些数字**不能证明**纯背景误报、多脸、远处小脸和不同光照的现场质量，也不代表 Zynq 速度。输入尺寸变体只是**同一训练权重的重新导出**，没有重新训练三遍。

模型版本锁：Ultralytics 8.4.135、pnnx 20260526、NCNN Python 1.0.20260526、板端 NCNN 源码 tag 20260526；320 模型及源码校验值在 `linux/studyboard_ncnn_face/DEPLOYMENT-MANIFEST.txt`。板端 NCNN 用 ARM hard-float SDK 编译，SIMPLEOMP 用双核 pthread 并行，不依赖缺失的 `libgomp`。若改变运行时或模型，必须重新核对导出 blob 名、输出维度、依赖库和真实板端结果；不要仅凭 PC 成功就覆盖 SD 基线。NCNN 的 INT8 路径属于**未来独立试验**，官方流程包含校准表和量化步骤，不能仅改一个编译开关就假定本项目已加速；见 [NCNN 官方量化说明](https://github.com/Tencent/ncnn/wiki/quantized-int8-inference)。

## 6. 历史问题教会我们什么

| 事件 | 真正需要学会的判断 |
| --- | --- |
| BitBake 报成功但找不到 `.ko` | 成功是 recipe 任务成功，不等于你搜索的路径正确；检查 recipe workdir、打包产物和 `rm_work`，避免对整个 `build/tmp` 盲目 `find`。 |
| SDK 安装后 `$CC` 找不到 | 必须区分 `components/yocto` 的构建环境和 `images/linux/sdk/environment-setup-*` 的独立 SDK；检查 `command -v`、`$CC --version` 和 sysroot。 |
| ARM 程序提示 `No such file or directory` | 先看文件是否存在，再看 ELF 解释器 `/lib/ld-linux-armhf.so.3` 和动态库；这条报错不必然表示源路径拼错。 |
| 有芯片 ID、但 `frame 0` 超时 | SCCB 控制平面与 DVP 像素数据平面是两回事；看 S2MM IRQ、V4L2 帧和物理连线/时钟。历史具体根因并未被单一证据完全锁定。 |
| LCD DMA 完成却黑屏 | DMA 描述符完成不等于 PL LCD 接收端接受了期望的持续视频时序；实物验证后改为连续 MM2S。 |
| `300` 运行十余秒后停屏 | 这是要求采集 300 帧后正常退出，不是“运行一会儿卡死”。持续运行要传 `0`。 |
| ping 通但 scp/SSH 失败 | IP、TCP 端口、认证、旧 `ssh-rsa` 主机密钥和 host-key 校验是不同层。不要关闭主机密钥验证来绕过警告。 |
| 重启后 `/home/root` 文件消失 | 不能假设临时上传位置持久；已验证运行包放在 SD ext4 的独立目录并保留校验值。 |

## 7. 以后改代码时先问哪一层

| 想改什么 | 先看哪一层 | 最小回归 |
| --- | --- | --- |
| OV5640 寄存器/曝光 | `ov5640_init/`；同时核对传感器输出时序 | ID/读回、5 帧 V4L2、实物画面 |
| DMA、帧格式、分辨率 | `.dtsi`＋内核驱动＋应用常量＋PL 约束 | 旧诊断、V4L2 sequence/payload、LCD 颜色/行对齐 |
| 检测阈值或后处理 | `face_detector.cpp`/启动脚本 | 同一标注样本前后对比，误报/漏报 |
| 模型尺寸或网络 | 训练/导出＋`face_detector.cpp`＋模型路径 | PC 输出形状/指标、ARM 编译、板端速度/质量 |
| LCD 更新频率 | `STUDYBOARD_PREVIEW_STRIDE` 或显示通路 | 捕获完整性、LCD 发布耗时和目视撕裂 |
| 开机自动运行 | 启动服务/SD 挂载/网络配置 | 多次冷启动、失败日志、手动回退 |

每次只改变一个变量，保留原目录和 SHA256；一个阶段的 PASS 不能自动替代下一阶段的实物验收。
