# 故障排查与验收

定位顺序固定为：**电源/启动 → SD 和 Linux → 网络 → OV5640 配置 → PL/VDMA → V4L2 → 模型推理 → LCD 输出**。前一层未通过，后一层的错误多半只是连锁结果。以下命令除明确说明外在**开发板**执行；先保留完整日志、时间、当前目录及所用包版本。

## 1. 十分钟定位树

| 关口 | 正常证据 | 不通过时先做什么 |
| --- | --- | --- |
| DONE、串口 | 上电后 FPGA 配置完成，串口出现 U-Boot/Linux/登录 | 检查供电、启动模式、BOOT FAT 中 `BOOT.BIN`/`image.ub`；不要先排 SSH |
| SD/Linux | `mount \| grep mmcblk0p2` 有 ext4，`uname -r` 与包内 `KERNEL-RELEASE` 一致 | 用串口查 `dmesg` 和 SD；不在未知分区执行修复/覆盖 |
| 网络 | eth0 `LOWER_UP`，Windows 与板同一 `/24`，可双向 ping | 通过串口核对静态地址；网络只是传输/管理路径，非摄像头必需 |
| 传感器 | `ov5640-id` 为 `0x5640`；初始化 248 寄存器、关键读回均 PASS | 停止后续启动，保存 I²C 错误；不要无限重复初始化 |
| PL/VDMA | V4L2 测试实际收到帧，相关 IRQ 计数增加 | 检查 bitstream/设备树/时钟/DVP 信号；传感器 ID PASS 不能跳过此关 |
| V4L2 | `studyboard-v4l2-test /dev/video0 5` 五帧、长度 921600、摘要变化 | 排独占占用、驱动版本与 frame0 timeout；不要先改模型 |
| NCNN | 程序加载正确尺寸的 param/bin，`inference` 计数增长 | 核查文件、动态库、导出版本、输入输出张量 |
| LCD | 屏幕持续更新，框与 PPM 对齐；`lcd_summary` 增长 | 区分 `matched` 与 `preview`，查 LCD DMA/像素顺序/物理连线 |

`DONE` 指示灯和启动介质故障曾发生过，但记录不足以认定唯一根因。再次发生时，先拍下指示灯、保存**从上电开始**的串口日志；仅凭 ping 不通无法判断是板没启动还是仅网络丢失。

## 2. 常见症状与证据边界

### 2.1 `ov5640-init` 的 `NAK bailout` 或写第 7/12 个寄存器失败

`ov5640-id` 读到 `0x5640` 只说明 I²C/SCCB 路径在读取芯片 ID 时可用。它不证明 248 次连续写入都可靠，更不证明 DVP 图像到达 PL。项目的 bundle-local `ov5640-init` 对单寄存器写做了有限重试，并用关键寄存器读回确认；当脚本已报告失败时应保存首次错误、上电状态和 I²C 日志，先停下来排供电/时钟/复位/接线/总线干扰。不要一遍遍强制初始化直到偶然通过；此板曾出现初始化重试之后 frame0 等待超时。

### 2.2 `Timeout waiting for frame 0`、采集 IRQ 不增加

这表示驱动启动了 VDMA/V4L2，但没有收到预期的第一帧完成事件。实际曾观察到：`/dev/video0` 注册成功、`ov5640-id` 成功、寄存器读回 PASS，但 V4L2 和旧 sysfs capture 均 frame0 timeout，DMA IRQ 不增长。对这个情形，重新加载相同模块也未恢复，因而不能把故障归咎于 NCNN 模型。停止运行，记录 `grep xilinx-dma-controller /proc/interrupts` 的前后计数、`dmesg`、当前 bitstream/内核/模块、是否重新初始化过传感器，然后**干净重启**作为受控恢复实验。若重启仍失败，再排 OV5640 PCLK/VSYNC/HREF/DVP、PL 接收链路、设备树 DMA 绑定和时钟。不要随意用 `devmem` 写 VDMA 寄存器；原始读值没有充分上下文，不等于根因。

### 2.3 `fopen ... model.ncnn.param failed` 或程序 `No such file or directory`

前者多是模型路径不在当前 SD 包、复制缺失或拼写错误；检查 `ls -lh`、目录和 `sha256sum -c SHA256SUMS`，确认 param/bin 来自同一次导出。后者如果 `ls` 已证明 ELF 文件存在，还要检查是否是动态装载器或依赖库缺失：

```sh
file ./studyboard-ncnn-face-lcd
/lib/ld-linux-armhf.so.3 --list ./studyboard-ncnn-face-lcd
```

若板端没有 `file` 命令，把 ELF 复制到 Ubuntu 虚拟机再检查；`ld-linux-armhf.so.3 --list` 应在板端运行。过去曾有安装 SDK 前交叉编译器不在 PATH、板上 `libstdc++.so.6`/`libgcc_s.so.1` 依赖要匹配的情况。不能把“文件存在”直接当成“可执行”；也不能随意复制其他 ARM 发行版的 C++ 库。

### 2.4 LCD 黑屏、停帧、只有原图或没有框

先确认启动模式和运行时计数：

```sh
P=/sys/bus/platform/devices/studyboard-frame-capture
cat "$P/lcd_status"
grep xilinx-dma-controller /proc/interrupts
```

`matched` 模式只有推理完成后才发布匹配的带框帧，320 输入可接近一秒才变一次；“屏幕像暂停”不一定是 DMA 故障。`preview` 模式让原图持续更新，复用最近一次检测框；检测仍可能只有约 1–2.6 次/秒。过去单次写入 LCD DDR 缓冲后屏幕不持续刷新，后来驱动加入 continuous-copy 模式、重复 frame store 和前后缓冲，才实现连续显示。若 `lcd_summary` 增长而屏幕确实不变，需要进一步观察显示 DMA IRQ 的**增量**、画面内容是否本来静止、物理 LCD 接线/供电和像素格式。不要只拿 `lcd_summary` 判定视觉正确。

### 2.5 `faces=0`、红框偏移、识别慢

先在 PPM/PNG 上核对相机原图是否正常、光照/距离/姿态是否落在训练集范围；再核对运行输出中的模型尺寸和张量形状。`192` 速度更高，但小脸像素信息更少；该项目只有小规模且一图一脸的测试集，现场多人/遮挡/逆光等没有充分量化。红框偏移要沿 BGR→RGB、letterbox 的缩放和 padding、输出解码、逆映射、LCD BGR24 顺序逐级检查，而非只改阈值。推理慢需先看 `average_ms: inference`，不要拿 28.5 fps 摄像头或 LCD 发布帧率当作模型速度。

### 2.6 SSH/SCP 失败或重启后文件“丢了”

- `ping` 不通：串口先检查 Linux 是否启动、`eth0` link/IP；直连线默认无 DHCP。
- `no matching host key type ... ssh-rsa`：受控实验板连接命令中增加 `-o HostKeyAlgorithms=+ssh-rsa`；旧 SCP 协议还需 `-O`。
- `REMOTE HOST IDENTIFICATION HAS CHANGED`：串口核验板端指纹后再更新 Windows `known_hosts`，不要关闭校验。
- SCP 报远端目录不存在：在**板端**先核对 SD ext4 已挂载、目录存在；路径不同不能盲传。
- `/home/root` 下应用消失：历史上重启后确实发生，持久包应放 SD ext4；不是每次上电都重新编译/上传。

### 2.7 编译成功却找不到 `.ko`，或 SDK 构建失败

PetaLinux `Successfully built` 只能说明 BitBake 任务成功，不表示 `.ko` 一定落在你猜测的位置。优先检查该 recipe 的 `build/tmp/work/.../studyboard-frame-capture/...` 工作目录、`packages-split`、recipe 的 `do_install` 和部署脚本；避免对整个 `build/tmp` 用会沿循环链接遍历的 `find -L`。SDK `do_fetch` 受 `BB_NO_NETWORK` 或镜像缺包限制时，缺失源码包需要按 recipe 指定 URL/校验和补齐，再重新构建；不修改校验值来“绕过”下载问题。SDK 安装后要使用 `images/linux/sdk/environment-setup-*`，再 `command -v arm-xilinx-linux-gnueabi-gcc` 和 `$CC --version` 验证。主机 Ubuntu 版本警告和 `/tftpboot` 拷贝失败，当其他任务成功时并不等同 `.ko`/应用构建失败，但仍应记录。

## 3. 已验收与待验收

| 项目 | 目前证据/状态 | 还需要什么 |
| --- | --- | --- |
| 摄像头—V4L2 | 300/300、9000/9000 等运行中 `sequence_gaps=0`、`bad_payloads=0`；约 28.5 fps | 持续监测供电/不同批次板卡 |
| 人脸框位置 | 现场图像和 LCD 曾看到红框对准人脸 | 更多场景、多人与边界案例量化 |
| 320 连续预览 | 9000 帧、314.828 秒；LCD 4485 次发布，用户确认全程更新；重启/掉电后手动启动正常 | 更长可靠性与自动启动（若需要） |
| 192 速度 | 600 帧对照约 383.37 ms/次、2.61 次/秒；短时现场 530 帧/18.571 秒、48 次推理，目视与 224 稳定性接近 | **192 的同等级长测及多场景精度验收** |
| 推理资源 | 2 线程 SIMPLEOMP，CPU 上 320 约 1 次/秒、192 约 2.61 次/秒 | CPU/内存/温度/功耗长测，若目标更高需模型或硬件方案 |
| 屏幕视觉质量 | 预览模式持续更新；已验证检测框可显示 | 运动时撕裂/框滞后量化；必要时实现真正垂直同步缓冲交换 |
| 自动恢复 | `start-face-lcd.sh` 有启动前检查、已知可用回退包保留 | 未部署自启动服务和看门狗；不宣称无人值守 |

核心事实：当前完成的是**可重复演示、可手动恢复的原型**，不是已经经过生产级稳定性、准确率和无人值守验收的产品。

## 4. 建议的下一轮验收方案

1. 保留 320 包不动，对 192 版本用 `start-face-lcd.sh 9000` 做与 320 可比的长测：保存完整日志、退出码、摄像头无缺帧/坏 payload、LCD 全程肉眼持续更新、最后 PPM 框位置。
2. 建场景清单：一人/多人/无人、近中远、转头/遮挡、强弱光、快速移动；每类记录样本数和漏检/误检。先定通过阈值，再决定 192 是否替代 320 默认值。
3. 记录运行时温度、可用内存、CPU 占用和过夜稳定性。若必须提高检测 FPS，可进一步评估更轻模型、INT8 量化或 PL 加速，但需逐项验证精度与真实板上速度；不能把 PC 速度套到 ZYNQ。
4. 若产品目标是“上电即用”，再设计开机服务、异常重启、日志滚动与安全回退；不要在还未完成 192 验收时直接替换已知可用包。

验收记录模板：`日期｜板卡/电源/镜头｜BOOT.BIN/image.ub 哈希｜uname -r｜bundle 目录和 SHA256SUMS｜模型尺寸/模式｜采集帧数与秒数｜sequence_gaps/bad_payloads｜推理次数/均值/最大值｜LCD 发布次数｜多场景检出统计｜退出码｜原始日志/PPM 路径`。
