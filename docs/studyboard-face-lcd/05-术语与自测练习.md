# 术语、学习路线与自测练习

本章把系统里每个缩写映射到可观察的现象。建议先读 01→02，再独立操作 03→04，最后不看答案完成本章练习。**没有文档能自动保证掌握**；标准是你能解释数据流、独立复现、定位故障并安全回退。

## 1. 硬件和 Linux 术语速查

| 术语 | 在本项目中的意思 | 怎么验证自己理解 |
| --- | --- | --- |
| PS / PL | ZYNQ 的 ARM 处理系统 / FPGA 逻辑。Linux、NCNN 在 PS；相机接口与视频 DMA 连接 PL | 能指出哪一层负责图像采集、哪一层执行 YOLO |
| OV5640 | 摄像头传感器；控制与像素是两条路径 | 知道读到芯片 ID 不代表视频有帧 |
| SCCB / I²C | 传感器寄存器配置总线，板上 `/dev/i2c-0`，地址 `0x3c` | 解释 248 次写和关键读回的作用 |
| DVP / PCLK / VSYNC / HREF | 相机像素并行总线、像素时钟和行/帧同步 | 解释为何 I²C PASS 仍可能 frame0 timeout |
| AXI4-Stream / VDMA | PL 内视频流及内存搬运。S2MM 写采集帧到 DDR，MM2S 从 DDR 送 LCD | 画出两条 DMA 箭头方向 |
| CPU 虚拟地址 / DMA 地址 | CPU 读写缓冲所用地址 / 硬件 DMA 访问地址，不能混同 | 解释驱动为何要分配 DMA 缓冲 |
| coherent DMA | CPU 与设备共享的一类一致性 DMA 内存；本项目驱动为三帧分配 2,764,800 字节 | 算出一帧字节数和三帧总量 |
| V4L2 / vb2 | Linux 视频设备接口 / 内核视频缓冲框架 | 能说出 `/dev/video0`、REQBUFS、QBUF、DQBUF 的角色 |
| MMAP | 应用映射 V4L2 缓冲，减少额外跨内核/用户拷贝 | 能按顺序描述申请、映射、入队、取帧、再入队 |
| BGR24 / RGB888 / RGB565 | 三种像素表示。本项目 V4L2 帧在内存中是 B、G、R 各 1 字节；传感器配置为 RGB565；PL/驱动链路做格式转换 | 解释为什么看到 `BGR3` 不等于颜色一定错 |
| sequence / bytesused / digest | 帧序号 / 实际有效负载字节数 / 用来比较画面是否变化的摘要 | 知道 `sequence_gaps=0` 与 `digest_changes` 各自证明什么 |
| mailbox | 采集线程与推理线程之间的“最新帧”邮箱 | 解释 `skipped_stale` 很大为何可能是合理设计 |
| letterbox | 等比例缩放后填边框，使 640×480 输入变为方形模型输入而不变形 | 算出 192 输入时缩放后 192×144、上下各填 24 |
| CHW / float32 / normalize | 神经网络输入按通道、高、宽排列，浮点数，像素通常除以 255 | 区分它与摄像头原始 BGR24 字节布局 |
| YOLOv8n / NCNN | 训练用的目标检测网络 / 板端轻量推理框架 | 解释 `best.pt` 与 `model.ncnn.param`/`.bin` 的边界 |
| NMS | 非极大值抑制，按重叠度清理重复框 | 知道 `iou=0.45` 用在去重，而 `conf=0.25` 用在候选筛选 |
| mAP50 / mAP50-95 | 测试集检测精度指标，后者覆盖多个 IoU 阈值 | 解释为何 19 张验证图高分不保证现场无人/多人表现 |
| SIMPLEOMP | NCNN 使用的轻量 OpenMP 并行实现，此项目以双核/2 线程运行 | 分辨编译时支持和运行时 `threads=2` |
| front/back LCD buffer | 显示中的缓冲 / 准备更新的缓冲 | 解释连续显示与潜在撕裂为何能同时存在 |
| `boot_id` | Linux 本次启动的唯一标记 | 解释为什么传感器只初始化一次/次启动 |
| SDK / sysroot | 交叉编译工具链 / 目标板 ABI、头文件和库的根目录 | 能区分 Ubuntu 主机程序与 ARM 目标程序 |
| `BOOT.BIN` / `image.ub` | ZYNQ 启动与 Linux 镜像相关文件 | 知道日常调模型尺寸不需更新它们 |
| SSH host key | 远端主机身份密钥，不是 root 登录密码 | 解释换 key 警告为何不能无条件接受 |

## 2. 按代码建立心智模型

建议每读一个函数都写下四点：输入、输出、缓冲所有权、失败后的清理动作。由外到内按这个顺序读：

1. `linux/studyboard_ncnn_face/start-face-lcd.sh`：开机前置检查、boot_id、模块切换、回退。问：哪些检查会在加载 LCD 模块之前阻止继续？
2. `linux/studyboard_ncnn_face/run-face-lcd.sh`：环境变量怎样选择模式/模型、应用参数怎样传入。问：为何默认 320 + matched 不适合速度演示？
3. `linux/studyboard_ncnn_face/studyboard-ncnn-face.cpp`：V4L2 缓冲循环、双槽邮箱、推理线程、性能统计。问：为什么不能让缓慢推理独占采集缓冲直到算完？
4. `linux/studyboard_ncnn_face/face_detector.cpp`：BGR→RGB、letterbox、NCNN 输出、NMS、坐标逆映射、红框。问：若忘了减去 padding，框会偏向哪里？
5. `linux/studyboard_ncnn_face/lcd_output.cpp`：每帧完整写入 `lcd_frame` 后 `lcd_commit`。问：中途只写一半为何不允许提交？
6. `linux/studyboard_frame_capture/studyboard-frame-capture.c` 与设备树：V4L2/VB2、DMA 资源、LCD 连续显示、独占状态。问：S2MM、MM2S 分别服务谁？
7. `linux/ov5640_linux_init/ov5640-init.c`：I²C 写重试、读回；对照硬件手册理解寄存器，但不要随意改表。问：哪条日志能证明传感器已经开始实际输出图像？

对每一步先画一条数据箭头，再把 `bytes=921600`、`[1,5,756]`、`source_sequence` 这些日志标到箭头上。之后再尝试修改代码，比先从 30 MB 静态链接 ELF 看起容易得多。

## 3. 自测题：先独立作答

1. 摄像头是 640×480，V4L2 内存格式 BGR24。一帧和三帧 DMA 缓冲分别是多少字节？
2. 192 方形输入保持 4:3 宽高比时，图像内容大小与上下 padding 是多少？为什么不能直接把 640×480 拉伸成 192×192？
3. 在日志中采集是 28.55 fps、LCD 发布约 14 fps、模型 2.61 次/秒。三者分别是什么？为什么不是矛盾？
4. `inference_summary: processed=48 skipped_stale=482` 是否意味着 482 帧采集失败？为什么？
5. `ov5640-id=0x5640`、全部关键寄存器 PASS，但 `/dev/video0` 一直 `Timeout waiting for frame 0`，你会先检查哪一层？为何不先换模型？
6. `model.ncnn.param` 和 `.bin` 分别是什么？改为 224 模型时只替换 `.bin` 是否安全？
7. 在板上如何启动 192 的无限时长 `preview`？如何安全退出和回到已知可用的 320 包？
8. 为什么在 SSH 会话中执行 `ip addr flush dev eth0` 危险？直连网线没有 DHCP 时怎么连接？
9. 一条 `lcd_summary: frames=135` 说明了什么，不能证明什么？若画面不动还需看哪些证据？
10. 验证集 19 张、mAP50=0.995，测试集 108 张且每图一张标注人脸。为什么不能直接宣称“真实场景准确率 99.5%”？
11. 修改用户态后处理与修改 PL bitstream，两种改动的构建/部署范围有什么不同？
12. 如何证明 192 可正式替换 320 默认值？除了速度，还缺哪些实验？

## 4. 参考答案要点

1. `640×480×3 = 921600`；三帧 `2764800` 字节。V4L2 用户态另有申请的四个缓冲，不能把两个不同缓冲池混为一谈。
2. `192×144`，上、下各 `24` 像素。直接拉伸会改变脸的几何形状，可能影响检测与坐标还原。
3. 分别是传感器/采集、LCD 发布、神经网络推理。独立线程与最新帧邮箱允许采集/显示快于推理。
4. 不是。邮箱选择新图并跳过过期图；仍要看 `sequence_gaps`、`bad_payloads`、IRQ 与现场画面来判断采集健康。
5. 先查 DVP→PL→VDMA S2MM→驱动第一帧/IRQ，核对 bitstream、设备树、时钟和初始化顺序。模型还没拿到任何帧，与 frame0 timeout 不同层。
6. `.param` 是网络结构与层连接，`.bin` 是权重；必须同次导出、相同尺寸且接口形状被程序支持，不能拼装。
7. 使用 03 章的 `STUDYBOARD_LCD_MODE=preview STUDYBOARD_MODEL_SIZE=192 sh ./start-face-lcd.sh 0`；`Ctrl+C` 停止，确认 DMA 停止和统计，然后进入独立的 `face-lcd-preview-20261012-01` 目录启动 320。
8. 会清掉当前连接所依赖的 IP，SSH 自身断线。Windows 网卡设 `192.168.10.1/24`、板卡 eth0 设 `192.168.10.2/24`，最好从串口设置与诊断。
9. 只说明向 LCD 驱动完成了 135 次发布，不能证明物理屏刷新、内容变化、框正确。要看屏幕、MM2S IRQ 增量、最后 PPM、模式和可能的静态场景。
10. mAP 是特定样本/阈值上的检测指标；样本量与场景分布不足，且缺无人、多人、遮挡等负例/复杂例，不能外推成普遍正确率。
11. 前者通常只需 SDK 编译应用并单独传新版本包；后者牵涉 PL、设备树和启动镜像，需更严格的 SD 启动介质更新/回退。都应记录版本与校验值。
12. 与 320 对等的长测、不同场景逐类评估、漏检/误检、CPU/温度/内存与断电重启复测、LCD 视觉质量，以及事先确定的通过阈值。当前只足以称“有前景的速度试验”。

## 5. 能否独立接手的验收表

学完后请在**不看命令复制记录**的前提下自评并实操：

| 能力 | 完成证据 |
| --- | --- |
| 画出两条路径 | 相机经 S2MM 到 DDR/V4L2；显示经 MM2S 到 LCD；能标注 PS/PL 和 BGR24 |
| 启停系统 | 独立选择 192 或 320、preview 或 matched，解释 `0`/`300`、保存日志与 PPM |
| 读统计 | 正确区分三种速率、`skipped_stale`、`sequence_gaps`、`bad_payloads` |
| 定位故障 | 给出 frame0 timeout、模型加载失败、SSH host key 变化的安全第一步 |
| 版本治理 | 找到已知可用包，验证内核 release 与哈希，新版本独立目录安装并可回退 |
| 评估改进 | 能写出 192 长测和多场景测试计划，并说明什么证据才允许改默认值 |

任何一项仍需查手册是正常的；重复执行、讲给同伴听、保留自己的真实运行记录，才是从“会照着运行”到“掌握系统”的过程。
