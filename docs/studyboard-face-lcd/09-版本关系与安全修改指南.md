# 09｜源码、构建、模型与板端文件：版本关系和安全修改指南

本章把“改了哪个文件，生成什么，拷到哪里，如何证明真的用了新版本”串起来。它不是要求现在重建：当前包能用时，日常运行不需重新训练、编译、拷贝或重刷 SD。

## 1. 五种不同的文件身份

```text
正本源码                    生成/部署中间物                     板端运行物
linux/*.c/*.cpp/*.sh  ─编译/打包──> output/.../app 或 update  ─校验/安装──> SD ext4 trial/
RTL + Vivado Tcl + XDC ─实现/导出──> bitstream/XSA             ─PetaLinux──> BOOT.BIN / image.ub
best.pt + export 参数  ─NCNN导出──> model.ncnn.param + .bin     ─校验/安装──> face-model-尺寸/
PetaLinux recipe / DTS ─BitBake──> .ko / rootfs / device tree ─启动/热加载──> /dev/video0
```

`output/` 往往是**快照或交付物**，`build/` 往往是**工具工作区**，板端 SD 目录是**运行物**。同名文件并不自动同步。运行前应知道“正本→打包副本→板上试验目录”的哈希是否连贯。`DEPLOYMENT-MANIFEST.txt`、`SHA256SUMS` 和 `KERNEL-RELEASE` 分别帮助核查模型/源码记录、实际包字节和内核 ABI；三者不能相互替代。

## 2. 仅有本仓库时，哪些仍属于外部依赖

| 外部资产 | 目前位置/事实 | 对复现的影响 |
| --- | --- | --- |
| PetaLinux 2020.2 项目及 `project-spec/meta-user` | 历史操作在 Ubuntu `/home/ubuntu/petalinux/ALIENTEK-ZYNQ`；本仓库只有配套的 Linux 源/recipe/DTS 片段 | 单靠本仓库无法按原样重建当前 `image.ub`、完整 rootfs 与最终合成设备树。 |
| Vivado 2020.2 实际导入 PetaLinux 的 XSA、SD 上 `BOOT.BIN`/`image.ub` | 仓库有创建/构建脚本和部分 `build/v20` 产物，但板上启动文件哈希未在本章重新实测 | 不能仅凭脚本就断言上板 PL 版本；交付时需单独归档哈希与来源。 |
| ARM SDK、NCNN SIMPLEOMP 安装 | 历史路径分别在 `images/linux/sdk/`、`/home/ubuntu/ncnn-zynq-20260526-simpleomp` | 交叉编译应用须使用相同 target ABI/NCNN 头库；PC 本机 `g++` 不能替代。 |
| YOLO 原训练数据/完整训练日志 | Windows `E:/Yolo/ultralytics-main/newface` 与 `E:/Yolo/face_zynq/runs/...`；仓库仅有测试集副本、评估脚本、best.pt/导出模型部分材料 | 仓库可解释并验证导出模型，但若外部原始数据丢失，无法完整复现训练。 |
| 真实板卡/电源/OV5640/ATK-MD0430/连线 | 物理硬件 | 仿真、PC 精度和哈希校验都不能替代实物显示/帧完整性测试。 |

这些是**资料完备性限制**，不是现在系统不能运行。若将来要编成可交付的“从零教程”，应把上述外部资产的版本号、下载/授权来源、哈希、连接图及验收日志补成一份固定清单；不要把未知内容写成已知。

## 3. 常见修改的最小构建边界

| 修改 | 应改的正本 | 最小构建/部署 | 不应做的额外动作 |
| --- | --- | --- | --- |
| 采集帧数、192/224/256/320 切换、preview/matched | 不改代码；仅环境变量/参数 | 在已有 speed 或 preview SD 目录运行 | 不重训、不刷卡 |
| 预览抽帧频率、置信度、NMS 阈值 | `run-face-lcd.sh` | 复制**版本化**脚本到独立试验包，校验后测试 | 不用重编 NCNN/驱动 |
| 后处理、邮箱、PPM 或 LCD 发布逻辑 | `studyboard-ncnn-face.cpp`、`face_detector.cpp`、`lcd_output.cpp` | 已装 SDK + NCNN 库交叉编译 ELF；独立试验目录；主机测试+板端回归 | 不默认重刷 BOOT 分区 |
| 模型输入尺寸/权重 | 训练/导出配置，成套 `model.ncnn.param`/`.bin`；若输出接口变则改 detector | PC 数据集验证、ARM 加载/形状/速度/实物框测试 | 不只替换 `.bin`；不以 PC timing 估计 Zynq |
| 传感器模式、帧率 | `SDK/.../ov5640_init.c` 原表、生成器/`linux/ov5640_init`，必要时对应 PL/驱动几何 | 表生成核验、ARM init/读回、5 帧和长测 | 不无限重试 I²C、不只改 `0x3808` |
| V4L2 或 LCD 驱动 | `studyboard-frame-capture.c`、`.dtsi`、recipe | 与运行内核同版本 `.ko`；内核 release/哈希；独立包与回退 | 不在工作流中覆盖已知可用模块 |
| PL 帧差、LCD 写时序、引脚 | `rtl/`、`scripts/`、`constraints/` | HDL 仿真→综合/时序→bitstream/XSA→相配 PetaLinux/SD 版本化更新 | 不用单纯 `insmod` 代替 bitstream 更新 |

改代码前先列出“预期产生的新日志/画面/哈希”，否则容易花时间重编却实际运行了旧文件。特别是 `run-face-lcd.sh` 默认 320 + matched；在 speed 包试 192 必须显式传 `STUDYBOARD_MODEL_SIZE=192` 和 `STUDYBOARD_LCD_MODE=preview`。

## 4. 2026-10-13 速度优化包是怎样形成的

1. Windows 同一 `best.pt` 分别导出 192、224、256 NCNN；`output/face_speed_256/eval.py` 对同权重的 PyTorch 输入尺寸做 test split 对照，`eval_ncnn.py` 对导出 NCNN 做 test split 验证。`output/studyboard_face_speed_20261013/models/{192,224,256}` 是对应 param/bin/metadata 副本。
2. Ubuntu 虚拟机的 `build-speed-variants.sh` 要求**新 shell**、正确 SDK 与 NCNN SIMPLEOMP 静态库，只重编用户态 ELF，生成 `speed-update-20261013-01` 和 `SHA256SUMS`。脚本没有重编 NCNN、本次内核、320 模型、bitstream 或 `image.ub`。
3. Windows 使用 SCP 传输更新目录。板端 `install-speed-variants.sh` 先校验更新，再从已知可用的 320 preview 包复制一个临时目录，合入新程序和三套模型，重新制作 SHA256，最后形成独立 `face-lcd-speed-20261013-01`，不覆盖 preview 包。
4. `compare-speed.sh 600` 依次测 320 首轮、224、256、192、320 尾轮。首尾 320 可检查温度/环境随时间变化造成的性能漂移。最后由人眼和板端日志共同决定试用 192，而不是由 PC mAP 单独决定。

这套“母本→临时目录→完整校验→独立试验目录→对照回退”的版本治理，正是之前反复插拔、编译、找不到二进制时积累出来的可复用流程。试验目录已存在时安装脚本故意拒绝覆盖，**不应为了强行再装而删除已知可用目录**；新试验应使用新的版本号/目录、先备份再验收。

## 5. 核对版本的只读命令（不要混终端）

板端在相应 SD bundle 目录：

```sh
uname -r
cat KERNEL-RELEASE
sha256sum -c SHA256SUMS
ls -lh studyboard-ncnn-face-lcd studyboard-frame-capture.ko face-model/model.ncnn.param face-model/model.ncnn.bin
cat /proc/sys/kernel/random/boot_id
```

Ubuntu VM 检查所用 ARM 工具链而非主机 GCC：

```sh
command -v arm-xilinx-linux-gnueabi-gcc
echo "$SDKTARGETSYSROOT"
arm-xilinx-linux-gnueabi-readelf -h /path/to/studyboard-ncnn-face-lcd
arm-xilinx-linux-gnueabi-readelf -d /path/to/studyboard-ncnn-face-lcd
```

Windows PowerShell 比对本机两个源副本：

```powershell
Get-FileHash "E:\zynq\github\ZYNQ_ov5640_hdmi_frame_difference-master\linux\studyboard_ncnn_face\face_detector.cpp" -Algorithm SHA256
Get-FileHash "E:\zynq\github\ZYNQ_ov5640_hdmi_frame_difference-master\output\studyboard_face_speed_20261013\app\face_detector.cpp" -Algorithm SHA256
```

上面 Ubuntu 的 `/path/to/...` 是占位符，需换成真实已构建路径；不要复制占位符运行。`SHA256SUMS` 只能证明包内文件与清单一致，不能证明芯片已经运行这些字节；还要结合脚本实际路径、`uname -r`、加载模块的 `modinfo`/内核日志、模型输入形状和板上运行结果。

## 6. 本轮文档工作没有做什么

本轮补文档没有重新训练、没有修改驱动算法、没有编译 ARM/PL、没有向开发板上传、没有改 SD 启动分区。文档中涉及的帧率/验收来源于既有日志；读代码所得的推断与“上板已实测”已分开标注。若未来任何代码或模型变化，请把版本号/日期、源哈希、构建命令、原始日志和回退包位置同时更新到开发记录与本手册。
